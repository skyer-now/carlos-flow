## 阶段三：四门面、自动变异与任务隔离（拟发布 v3.0.0）

阶段二完成后基于其已验收提交立新卡。此阶段涉及对外接口变更，使用主版本号3。

### 四门面收敛

1. 先建立唯一动作路由表，覆盖全部22个底层能力，包括原门面遗漏的协议、模式、审计查询、用户原话、结果保存、差异和触发检查。冻结22行旧能力到门面动作、参数、错误、副作用、证据、正反例的对照矩阵；新增导出、AST和worktree动作另列，不能靠总数相同冒充覆盖完整。
2. 验证每个动作参数、错误、状态与证据语义，然后让外部 MCP 工具目录只展示四个门面。
3. 底层领域函数保留为内部实现，不保留外部可调用的旧工具入口；删除的是旧公开工具面，不是门禁底座。
4. Cindy 的向导和目录元工具继续承担宿主交互，业务目录只发现四门面；同步长验证续命、向导恢复及错误译文，避免只改名称导致接入退化。
5. 同步客户端、模板、帮助、迁移和测试，明确旧工具名不再可用。

### AST 自动负对照

1. 实施前核实解析器来源、许可证、体积与运行成本；不把正则替换描述成 AST。
2. 首批仅支持明确范围的 JavaScript/ESM 测试断言算子，不宣称覆盖所有语言或所有作弊。
3. 在隔离副本进行变异，正常代码验证通过、破坏关键断言或逻辑后测试必须失败；没有适用算子、解析失败、超时均不能记作成功。针对支持范围比较明确基线与当前测试AST，识别关键断言删除、跳过或弱化；剩余测试通过或无关变异被杀死不能抵消此类问题。必须加入“删掉关键断言但测试仍退出0”的真实负例；无法判断及支持范围外标未验证，不冒充已防护。
4. 记录算子、目标、摘要、命令和结果；保留既有改动前负对照证据与恢复机制，不偷偷替换其含义。区分断言敏感性探测与业务变异，不以恒失败断言或无关测试自证。语法、加载、依赖及基础设施失败不算杀死变异体。首批设文件大小、变异数量、总耗时和输出量预算；在npm安装产物及Cindy随包环境分别核实解析器，不假设Forge带入node_modules。

### 单人任务 Git Worktree

1. 从明确提交建立单任务工作区，使用安全的任务标识和独立状态路径。
2. 拒绝不明基线、路径越界、符号链接逃逸和脏主工作区的隐式迁移。
3. 任务执行、测试、快照和报告绑定该工作区，不能回到主目录执行。
4. 异常或有未交付改动时保留工作区；登记基线、真实路径与持久任务分支。清理须无运行任务、无工作区/暂存/未跟踪变化，成果有持久引用且已交付；通过Git原生移除，仅清理本工具登记的工作区，不全局prune、不递归删用户项目、不杀用户应用。工作区默认在用户明确的项目工作区根下，任务状态在CARLOS_FLOW_HOME的任务分区，记忆在同一存储根的项目分区；真实路径和共享Git身份必须校验，创建/登记中断可恢复。
5. 验证两个任务互不污染、错误路径拒绝、崩溃保留、正常退出和可恢复流程。

完成判定：外部发现四门面且完整动作可用；真实 AST 负对照能检出支持范围内的坏改动；真实 Git worktree 从创建到执行和受控清理可核验。

## 每阶段统一收尾

- 代码与文档同步：README中文默认、English介绍、更新日志、迁移说明、工具契约。
- 全链路验收：普通消息静默→触发占位→缺项拦截→补齐→executor领取并派发→验证与负对照→auditor独立领取及双轴审核→最终裁定。
- 发布前记录测试命令、退出状态、日志文件摘要和被审提交；审查失败则修复复验，不带病推进下一阶段。
- 独立审核通过后完成本地版本提交；核对远端、既有标签与npm版本作为发布准备，不移动或覆盖已发布版本。
- 此次明确授权三个阶段的开发、测试与收尾；不沿用其他任务的远端发布授权。未获得本次明确推送/发布指令时，收尾到本地已验收提交和发布准备报告，不自动推标签触发公开发布。
- 若当前任务另获明确发布授权：推标签→轮询CI→核对npm版本与完整性→干净沙箱实装→MCP核心流程验证→清理明确的临时产物。
- 不自动安装或重启当前使用的插件，不关闭主力应用。发布可用与本机已启用是两个不同状态，报告分别说明。
- 每阶段报告列出：完成范围、未完成项、测试及负例、审查裁定、提交/标签/发布状态、回滚方法和边界。没有真实证据的项目标“未验证”，不标通过。

## 风险控制

不承诺零延迟、永久不误触、全网最强、工具压缩带来固定比例提速。性能结论只能来自可复现测量。保留零常驻新增进程、低开销按需运行的方向；如AST解析器需要小依赖，先记录实际取舍，不借零依赖宣传隐瞒依赖。

任何权限拒绝、认证或源码证据缺失均按真实原因记录，不编造发布成功。用户已经授权自动处理，无须对已确定事项再次追问；安全或权限边界不能绕过。
